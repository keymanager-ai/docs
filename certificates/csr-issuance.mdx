KryptoVault Certificate Signing Request (CSR) provides a controlled way to generate certificate requests and route them through configured issuers for certificate issuance.

It connects key generation, request creation, issuer selection, signing, and certificate onboarding into a single governed lifecycle.

<Info>
  A CSR represents the identity and cryptographic information required by a Certificate Authority to issue a certificate. KryptoVault manages this process centrally so certificate requests can follow consistent security and governance controls.
</Info>

## CSR generation

KryptoVault can generate Certificate Signing Requests as part of a managed certificate lifecycle.

CSR generation can be associated with newly generated key material or existing cryptographic keys, depending on the issuance workflow.

## CSR lifecycle

A Certificate Signing Request progresses through a controlled lifecycle from creation to final outcome.

<Steps>
  <Step title="Created">
    The CSR is generated and enters the request lifecycle.
  </Step>
  <Step title="Validating">
    KryptoVault evaluates the request against applicable request and cryptographic requirements.
  </Step>
  <Step title="Submitted">
    The validated request is submitted to the configured issuer for certificate signing.
  </Step>
  <Step title="Signed">
    The Certificate Authority signs the request and returns the issued certificate.
  </Step>
  <Step title="Imported">
    The issued certificate is brought into KryptoVault Certificate Inventory and becomes part of the managed certificate lifecycle.
  </Step>
</Steps>

A request can also end in **Rejected** or **Cancelled** when issuance should not continue.

<Note>
  CSR lifecycle state represents the status of the certificate request. Once the certificate is issued and imported, the resulting certificate follows its own certificate lifecycle.
</Note>

## Request validation

Before a CSR is submitted for signing, KryptoVault can validate the request against applicable certificate and issuer requirements.

Validation helps ensure that the request is suitable for issuance and that its identity and cryptographic context are aligned with the configured certificate policy.

This provides a control point before the request reaches the Certificate Authority.

## Issuer-based certificate signing

KryptoVault routes validated CSRs to the issuer associated with the certificate request.

The issuer remains responsible for certificate signing and trust establishment, while KryptoVault provides orchestration, lifecycle visibility, and governance around the request.

<Tabs>
  <Tab title="ACME">
    KryptoVault can route certificate requests through an ACME-compatible issuer for automated certificate issuance.

    This model is well suited to environments where certificate enrollment and renewal are expected to operate with minimal manual intervention.
  </Tab>
  <Tab title="Vault PKI">
    KryptoVault can use HashiCorp Vault PKI as an issuer for application, infrastructure, and cloud-native certificate workflows.

    Vault performs the signing operation while KryptoVault manages the request and resulting certificate within the broader lifecycle.
  </Tab>
</Tabs>

## Issuance processing

The issuance process connects CSR creation with the configured Certificate Authority and the managed certificate inventory.

<Steps>
  <Step title="Generate request">
    KryptoVault creates the CSR and establishes its cryptographic context.
  </Step>
  <Step title="Validate request">
    The CSR is checked before being routed for signing.
  </Step>
  <Step title="Submit to issuer">
    The request is sent to the configured Certificate Authority or issuer integration.
  </Step>
  <Step title="Issue certificate">
    The Certificate Authority signs the CSR according to its own certificate policy and trust model.
  </Step>
  <Step title="Onboard certificate">
    The resulting certificate is returned to KryptoVault and incorporated into Certificate Inventory.
  </Step>
</Steps>

## Certificate onboarding

Issued certificates become managed certificate assets in KryptoVault rather than remaining isolated issuance outputs.

Once onboarded, the certificate can participate in expiration monitoring, trust validation, cryptographic analysis, risk assessment, Certificate Store association, renewal, and lifecycle tracking.

<CardGroup cols={2}>
  <Card title="Inventory" icon="certificate">
    The issued certificate becomes part of the centralized Certificate Inventory.
  </Card>

  <Card title="Certificate Store" icon="folder-tree">
    The certificate can be associated with the operational store where it is managed or intended to be used.
  </Card>
</CardGroup>

## Key and certificate association

CSR generation and certificate issuance remain connected to the cryptographic key used to create the request.

Maintaining this association is important for later certificate operations such as deployment, renewal, replacement, signing, authentication, and key rotation.

<Warning>
  Private-key operations are sensitive cryptographic activities and should remain restricted to authorized roles and controlled storage mechanisms.
</Warning>

## Multi-issuer operation

KryptoVault supports multiple issuer technologies within the same certificate-management environment.

This allows organizations to use different Certificate Authorities for different certificate populations while maintaining a consistent CSR and issuance workflow.

For example, an enterprise can use Microsoft AD CS for internal certificates, ACME for automated public-facing certificates, and Vault PKI for application or cloud-native workloads.

## Renewal through issuance

Certificate renewal can reuse the same managed issuance model.

When a certificate requires replacement, a new request can be generated and routed to the appropriate issuer while maintaining the certificate's operational context and Certificate Store relationship.

This supports continuity between the expiring certificate and its replacement.

## Governance and traceability

CSR and issuance operations are controlled through KryptoVault's role-based access model.

Organizations can restrict certificate request creation, issuer usage, signing-related operations, and lifecycle actions according to administrative responsibility.

KryptoVault also maintains request and issuance traceability so teams can understand how a CSR progressed, which issuer processed it, and how the resulting certificate entered the managed inventory.
