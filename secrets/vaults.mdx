KryptoVault **Vaults** are secure logical containers used to organize and manage Secrets within the Key Vault.

Each Vault provides its own namespace, Protection Key relationship, access controls, and secret-management configuration. A Vault can contain multiple Secrets, and each Secret can maintain multiple Versions.

<Info>
  A Secret belongs to exactly one Vault. The Vault provides the management boundary for how those Secrets are protected, accessed, versioned, and displayed.
</Info>

## Vault identity

Each Vault is identified by a human-friendly name and a unique namespace.

<CardGroup cols={2}>
  <Card title="Vault Name" icon="vault">
    Provides the recognizable name used to identify the Vault within Key Vault management.
  </Card>

  <Card title="Namespace" icon="folder-tree">
    Provides the unique Vault namespace. The namespace is fixed after the Vault is created.
  </Card>
</CardGroup>

Tags can also be associated with a Vault to support classification and search.

## Protection Key relationship

Every Vault is linked to a **Protection Key** when it is created.

<Steps>
  <Step title="Protection Key is available">
    A Protection Key is created in Protection Key Settings.
  </Step>
  <Step title="Vault is created">
    The Vault is associated with one Protection Key during creation.
  </Step>
  <Step title="Protection relationship is fixed">
    The selected Protection Key cannot be changed after the Vault is created.
  </Step>
  <Step title="Secrets are managed inside the Vault">
    Secrets created in the Vault operate within that Vault's protection and configuration model.
  </Step>
</Steps>

<Warning>
  The Protection Key relationship is immutable after Vault creation.
</Warning>

## Network access control

A Vault can restrict requests using network access control.

When network access control is enabled, requests must originate from the configured allowed IP ranges.

<Card title="Allowed Network Ranges" icon="network-wired">
  Vault access can be limited to approved CIDR ranges. When the control is disabled, the allowed-IP list is not required.
</Card>

## Secret-management configuration

Each Vault can define controls that apply to the Secrets managed inside it.

<AccordionGroup>
  <Accordion title="Web UI visibility">
    The Vault can control whether the Vault and Secret names are visible in the web interface. Secret values remain protected and are not exposed simply because list visibility is enabled.
  </Accordion>

  <Accordion title="Maximum versions">
    A Vault can define the maximum number of Versions retained per Secret. A value of zero represents unlimited versions, while configured limits are enforced per Secret.
  </Accordion>

  <Accordion title="Response wrapping">
    Response wrapping can be enabled so Secret values are returned through wrapped tokens. A time-to-live is configured when wrapping is enabled.
  </Accordion>

  <Accordion title="Mandatory expiry">
    A Vault can require every Secret to have a future expiry date.
  </Accordion>

  <Accordion title="Audit events">
    Vault configuration can determine whether successful and failed requests generate audit events.
  </Accordion>
</AccordionGroup>

## Vault configuration and Secrets

Vault configuration establishes the operating rules for Secrets before those Secrets are created.

**Protection Key → Vault → Secret → Version**

This keeps protection, access, expiry, versioning, and audit behavior connected to the Vault in which the Secret is managed.

## Vault lifecycle

Vault configuration has defined edit constraints.

Before Secrets exist, Vault settings such as network access control and configuration can be changed, except for the linked Protection Key. Once Secrets exist in the Vault, editing is more restricted and the Vault name and tags remain the primary editable Vault details.

Version limits can still be adjusted, but the configured limit cannot be reduced below the number of Versions already retained.

## Secret management from a Vault

A Vault provides the entry point for managing its Secrets.

From the Vault context, permitted users can review the Vault details and work with the Secrets assigned to that Vault while Secret values remain protected according to the configured visibility rules.
