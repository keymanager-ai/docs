KryptoVault **Vault Access Control & Data Protection** defines how access to a Vault is constrained and how Secret values are returned, retained, and audited.

These controls are configured at the Vault level so Secrets inside the Vault can follow a consistent operating model.

## Network access control

A Vault can enable network access control and restrict requests to approved IP ranges.

<Steps>
  <Step title="Enable network access control">
    Network access control is enabled for the Vault.
  </Step>
  <Step title="Define allowed IP ranges">
    Approved network ranges are configured using CIDR values.
  </Step>
  <Step title="Validate incoming requests">
    When the control is enabled, requests must originate from the configured allowed ranges.
  </Step>
</Steps>

<Info>
  When network access control is disabled, the allowed-IP list is optional. When it is enabled, allowed IP ranges are required.
</Info>

## Web UI visibility

Vault configuration can control whether users can see the Vault and its Secret names in the web interface.

When Web UI visibility is enabled, the Vault and Secret names can be listed, but Secret values are not exposed as part of that read-only list visibility.

<Card title="Protected Listing Visibility" icon="eye">
  Users can be allowed to see Vault and Secret names without exposing the underlying Secret values.
</Card>

## Response wrapping

KryptoVault can return Secret values through wrapped tokens instead of returning the value directly.

When response wrapping is enabled, the Vault also defines the token time-to-live.

<CardGroup cols={2}>
  <Card title="Wrapped Response" icon="box-archive">
    Secret values are returned through wrapped tokens when response wrapping is enabled.
  </Card>

  <Card title="Time-to-Live" icon="timer">
    Wrapped tokens use a configured lifetime, with the Vault defining how long the wrapped response remains valid.
  </Card>
</CardGroup>

## Mandatory Secret expiry

A Vault can require all Secrets to have a future expiry date.

When mandatory expiry is enabled, new Secrets must comply with the expiry requirement. The product requirements also support configuring a default expiry duration for use during Secret creation.

Supported default expiry durations defined in the requirements are:

- 1 month
- 3 months
- 6 months
- 12 months
- 24 months
- 36 months

## Version-retention control

A Vault can define the maximum number of Versions retained for each Secret.

A value of zero means unlimited Versions. When a limit is configured, it is enforced per Secret and works together with the Secret Version lifecycle.

<Warning>
  The configured maximum cannot be reduced below the number of Versions already retained for the affected Secret.
</Warning>

## Audit-event controls

Vault configuration can determine whether audit events are emitted for successful and failed requests.

<Tabs>
  <Tab title="Successful Requests">
    Successful-request auditing is enabled by default and can generate audit records for successful Vault activity.
  </Tab>
  <Tab title="Failed Requests">
    Failed-request auditing is enabled by default and can generate audit records when Vault operations fail.
  </Tab>
</Tabs>

## Control model

The Vault combines access and data-protection controls into one configuration boundary:

**Allowed Network → Vault Access → Secret Visibility → Response Protection → Expiry → Version Retention → Audit Events**

This gives each Vault its own operating profile while keeping the Secrets inside that Vault aligned with the same access and protection rules.
