title: "Service accounts"

KryptoVault **Service accounts** are represented in the current KeyManager requirements as **Service users**.

They provide a separate user type from normal Interactive users and are managed through the same centralized Users capability.

<Info>
  The current FRD defines Service users as locally authenticated accounts. It does not define API tokens, machine credentials, client secrets, or token-based service-account authentication.
</Info>

## Service account model

Service accounts are created with their own identity, Role Target, Role Name, local password, tags, description, and account status.

<CardGroup cols={2}>
  <Card title="Separate Account Type" icon="robot">
    Service users are maintained independently from Interactive users.
  </Card>

  <Card title="Role-Based Access" icon="user-shield">
    Service-user access is determined by the Role assigned to the account.
  </Card>
</CardGroup>

## Service account creation

<Steps>
  <Step title="Create Service user">
    The administrator selects the Service user type.
  </Step>
  <Step title="Assign identity">
    The Service user receives its unique username and descriptive account information.
  </Step>
  <Step title="Assign Role">
    A Role Target and Role Name are selected to define the account's authorization.
  </Step>
  <Step title="Configure local authentication">
    A local password is assigned according to the current password requirements.
  </Step>
  <Step title="Activate account">
    Service accounts are Active by default and can later be changed to Blocked.
  </Step>
</Steps>

## Account status

Service users use the same Active and Blocked account-status model defined for users generally.

A Blocked Service user is treated as inactive and cannot successfully authenticate.

## Relationship with Interactive users

<Tabs>
  <Tab title="Service">
    Uses local authentication according to the current requirements and is managed as a separate operational account type.
  </Tab>
  <Tab title="Interactive">
    Represents a person using the KeyManager portal and can be enabled for both local and SSO authentication.
  </Tab>
</Tabs>

This distinction allows KeyManager to separate user-facing access from service-oriented access while keeping both account types under centralized Role and status management.
