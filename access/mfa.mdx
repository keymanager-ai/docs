KryptoVault **Multi-Factor Authentication (MFA)** strengthens user authentication by adding an additional verification layer after the primary sign-in process.

It combines authenticator-based verification, recovery access, configurable enforcement policies, exemptions, user enrollment, and administrative visibility into a centralized authentication control.

<Info>
  MFA can be applied across local and SSO-based authentication flows while allowing administrators to control how strictly enrollment is enforced.
</Info>

## MFA security model

MFA introduces an additional identity-verification step between primary authentication and application access.

<CardGroup cols={2}>
  <Card title="Authenticator Verification" icon="mobile-screen-button">
    Users verify their identity using a 6-digit code generated by an authenticator application.
  </Card>

  <Card title="Recovery Access" icon="key">
    One-time recovery codes provide an alternative verification method when the authenticator app is unavailable.
  </Card>
</CardGroup>

This creates a layered authentication model:

**Primary Authentication → MFA Verification → Application Access**

## Platform-wide MFA

MFA can be enabled or disabled centrally for the platform.

When enabled, MFA behavior is determined by the configured enforcement model and the user's enrollment or exemption status.

When disabled, MFA enrollment, verification, and MFA-related prompts are not applied.

## Enforcement model

KryptoVault supports multiple MFA enforcement models to accommodate different authentication policies.

<Tabs>
  <Tab title="Optional">
    MFA enrollment is offered to users but is not required for access.
  </Tab>
  <Tab title="Strict">
    MFA enrollment is mandatory for all applicable users.
  </Tab>
  <Tab title="Strict for local users">
    MFA enrollment is mandatory for locally authenticated users, while SSO users can continue to rely on the authentication controls of their identity provider.
  </Tab>
</Tabs>

This allows organizations to balance centralized MFA enforcement with existing external identity-provider controls.

## User enrollment

MFA enrollment connects a user's KryptoVault account with an authenticator application.

<Steps>
  <Step title="Start enrollment">
    The user initiates MFA setup from their signed-in account.
  </Step>
  <Step title="Register authenticator">
    KryptoVault provides a QR code and manual key for registration in the authenticator application.
  </Step>
  <Step title="Verify authenticator">
    The user confirms the setup using a valid 6-digit authenticator code.
  </Step>
  <Step title="Activate MFA">
    MFA becomes active for the user after successful verification.
  </Step>
  <Step title="Generate recovery access">
    Six one-time recovery codes are generated for the user.
  </Step>
</Steps>

<Warning>
  Recovery codes are shown only when MFA enrollment is completed and each code can be used only once.
</Warning>

## Authentication flow

For enrolled users, MFA becomes part of the sign-in lifecycle.

After the primary login succeeds, the user receives only temporary access required to complete MFA verification.

Full platform access is granted only after successful MFA verification.

This applies to both:

- Local password authentication
- SSO authentication where MFA applies

## Recovery access

Recovery codes allow users to complete MFA when they cannot access their authenticator application.

Each recovery code is single-use and is removed after successful use.

<Card title="One-Time Recovery" icon="life-ring">
  Recovery codes provide an alternate MFA path without disabling the user's MFA enrollment.
</Card>

Once all recovery codes have been consumed, recovery-code authentication is no longer available.

## Grace-period enforcement

Strict MFA policies can include a grace period for users who have not yet enrolled.

During the grace period, users are encouraged to enroll but can continue into the platform.

After the grace period expires, enrollment becomes mandatory before access is granted.

If no grace period is configured, mandatory enrollment is applied immediately.

## MFA exemptions

MFA enforcement can exclude specific users or access contexts.

<CardGroup cols={3}>
  <Card title="IP Exemptions" icon="network-wired">
    Specific IP addresses or IP ranges can be excluded from MFA enforcement.
  </Card>

  <Card title="User Exemptions" icon="user-shield">
    Selected users can be excluded from MFA enforcement.
  </Card>

  <Card title="Break-Glass Access" icon="triangle-exclamation">
    Designated break-glass users can remain exempt from MFA requirements.
  </Card>
</CardGroup>

When a user is permanently removed from the platform, their MFA exemption is removed as well.

## Optional enrollment experience

When MFA is optional, users can be prompted to enroll after authentication.

They can continue without enrolling or choose not to see the optional enrollment prompt again.

<Note>
  A previously dismissed enrollment prompt does not prevent MFA enrollment from becoming mandatory if the enforcement policy changes.
</Note>

## MFA lifecycle

An enrolled user can disable MFA from their own account.

Disabling MFA removes:

- The authenticator association
- All remaining recovery codes

Re-enabling MFA requires a new enrollment.

MFA enablement and disablement are recorded as platform events, and email notifications are sent when an email address is available.

## User MFA visibility

Users can view their own MFA posture, including:

- MFA enabled status
- Enrollment status
- Remaining recovery-code count
- Applicable enforcement mode
- Whether an enrollment prompt is due

This gives users visibility into their authentication state without exposing MFA secrets.

## Administrative visibility

Administrators can monitor MFA adoption across the user population.

<CardGroup cols={2}>
  <Card title="Enrollment Visibility" icon="users">
    User records indicate whether each user is enrolled in MFA.
  </Card>

  <Card title="MFA Adoption" icon="chart-simple">
    Administrators can review total enrollment and filter users by enrolled or non-enrolled status.
  </Card>
</CardGroup>

MFA usage is also available as part of event visibility, allowing event records to be filtered according to whether MFA was used.

## MFA management lifecycle

The overall MFA lifecycle can be represented as:

**Enable MFA → Define Enforcement → User Enrollment → Verification → Recovery → Monitoring → Disable / Re-enroll**

This gives KryptoVault a centralized model for MFA policy, enrollment, authentication, recovery, and operational visibility.
